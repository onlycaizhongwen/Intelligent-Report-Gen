# 技能：模块设计

## Meta
- DependsOn: S5, S6
- Category: architecture
- Status: stable

## 一句话描述
根据架构方案和技术选型，进行领域边界、服务边界、部署边界、通信边界与网关边界设计。

## 输入
- `docs/skill-chain/architecture.md`：架构设计文档
- `docs/skill-chain/tech_stack.md`：技术栈选型文档
- `openspec/project.md`：OpenSpec 项目说明
- `openspec/specs/`：OpenSpec capability 目录

## 输出
- `docs/skill-chain/module_design.md`：模块设计文档（中文 Markdown）

## Prompt

你是一位资深系统架构师。
请完成以下工作：

1. **领域边界识别（先做，不得跳过）**：

   | 领域 | 类型（核心/支撑/通用） | 业务能力 | 数据所有权 | 边界理由 |
   |------|------------------------|----------|------------|----------|

   - 必须先识别核心领域、支撑领域、通用领域，再决定是否拆成服务。
   - AI 项目至少评估：业务主域、知识库域、文档处理域、RAG/检索域、LLM/Agent 编排域、用户权限域、审计计费域。

2. **模块 / 服务 / 部署单元三层拆分**：

   | 领域 | 领域模块 | 应用服务 | 部署单元 | 是否独立服务 | 拆分理由 |
   |------|----------|----------|----------|--------------|----------|

   - 领域模块是逻辑边界，应用服务是接口边界，部署单元是运行边界，三者不得混为一谈。
   - 没有独立数据所有权、独立扩缩容、独立发布节奏或明确职责边界的能力，先设计为模块，不得强行拆成微服务。
   - 必须区分“独立部署单元”和“部署单元内部模块”：如果多个 AI 能力运行在同一个 Python/FastAPI、Java 或其他应用进程内，应标为内部模块，不得把每个能力都写成独立服务；只有确实独立发布、独立扩缩容或独立运行时，才标为独立服务。

3. **服务边界决策矩阵**：

   | 候选服务 | 独立数据所有权 | 独立扩缩容 | 独立发布节奏 | 一致性要求 | 团队/职责边界 | 结论（服务/模块） |
   |----------|----------------|------------|--------------|------------|----------------|-------------------|

   - 数据强一致且事务紧密的能力优先放在同一服务内。
   - 高并发、耗时、资源类型差异明显的能力可独立服务，例如文档解析、Embedding、向量检索、报告生成、LLM/Agent 编排。
   - 权限、审计、计费、通知等横切能力必须说明是独立服务、共享模块还是网关能力。

4. **模块拆分**：

   | 模块名称 | 所属层级 | 核心职责 | 包含组件 |
   |----------|----------|----------|----------|

5. **模块依赖关系**：

   | 源模块 | 目标模块 | 依赖类型 | 通信方式 |
   |--------|----------|----------|----------|

6. **服务通信与数据一致性设计**：

   | 通信场景 | 源服务 | 目标服务 | 协议/模式 | 一致性策略 | 失败处理 |
   |----------|--------|----------|-----------|------------|----------|

   - 同步查询：HTTP / gRPC。
   - 长任务：消息队列 / 任务队列 / 事件驱动。
   - 流式响应：SSE / WebSocket。
   - AI 任务状态：事件驱动 + 状态表。
   - 文件处理：对象存储 + 元数据表 + 回调/事件通知。
   - 文件导出/下载必须设计完整闭环：导出请求 -> 异步执行 -> 写入对象存储或文件存储 -> 回写导出元数据与状态 -> 用户下载入口/链接 -> 下载审计。
   - 下载策略必须写默认规则：普通内部认证访问可优先使用短期预签名 URL；外部分享、严格审计、高敏权限或需要统一水印/脱敏控制时，优先使用后端代理流。无论哪种方式，都必须先校验权限并记录下载审计。
   - 跨服务审计写入优先采用事件驱动进入审计归属模块；避免多个服务直接写同一审计表。若确需直接写入，必须说明数据所有权、幂等键、失败补偿和查询边界。

7. **如果是混合选型项目，按生态分组**：

   **后端业务模块（按 S6 技术栈，例如 Java / Go / Node.js / Python）**：
   | 服务/模块 | 职责 | 数据所有权 | 端口 | 注册中心 |
   |-----------|------|------------|------|----------|

   **Python AI 模块（FastAPI）**：
   | 服务/模块 | 职责 | 资源特征 | 端口 | 依赖 |
   |-----------|------|----------|------|--------|

   **网关模块（按 S6 技术栈，例如 Higress / Nginx Ingress / Spring Cloud Gateway / Kong / Go Gin）**：
   | 网关能力 | 职责 | 端口/入口 | 路由规则 | 下游边界 |
   |----------|------|-----------|----------|----------|
   - 必须先读取 S6 技术栈表，再按实际网关选型生成网关模块；不得在技能中默认绑定某个框架或网关。
   - 当 S6 明确选择 Higress 时，按 **Higress 网关模块**设计，并写清楚：阿里巴巴开源、基于 Envoy + Istio 构建的云原生 AI 原生 API 网关。
   - 当 S6 明确选择 Higress 时，必须按三类职责拆分说明：K8s Ingress / Gateway 入口、微服务网关、AI 网关。
   - 当 S6 明确选择 Higress 时，必须体现安全与可观测职责：WAF、JWT/OIDC、HTTPS 证书自动续签、Prometheus Metrics、链路追踪、Wasm 插件热更新。
   - 当 S6 明确选择 Higress 时，必须明确哪些能力放在 Higress：外部路由、鉴权前置、限流熔断、灰度发布、模型 API 代理、MCP Server 代理、语义缓存；哪些能力放在业务服务：业务事务、领域规则、数据写入、审计落库。

8. **共享内核（Shared Kernel）**：

   | 共享组件 | 包含内容 | 被哪些模块依赖 |
   |----------|----------|----------------|

9. **如果是 AI 项目，额外设计 AI 服务边界**：

   | AI 服务/模块 | 职责 | 输入输出 | 是否独立部署 | 依赖服务 |
   |-------------|------|----------|--------------|----------|
   | 文档解析服务 | PDF/Word 解析 + 切片 | 原始文档 → 文本块 | 视文件规模决定 | 对象存储 |
   | Embedding 服务 | 文本向量化 | 文本块 → 向量 | 通常独立部署 | BERT / BGE |
   | 检索服务 | 向量相似度搜索 | 查询 → 相关文档 | 可独立部署 | Milvus |
   | LLM 代理服务 | 大模型调用 + RAG 编排 | 问题 + 上下文 → 回答 | 视 S6 技术栈和部署边界决定 | LLM SDK / AI Gateway / 模型代理 |
   | Prompt 管理模块 | Prompt 模板存储与版本管理 | 场景 → 模板 | 优先作为模块 | 数据库 |

   - `是否独立部署` 必须反映真实部署单元，而不是能力重要性。运行在同一 AI 服务内的文档解析、Embedding、检索、模型编排、引用评分等能力，应写为“否，随某服务部署；满足资源/吞吐/团队边界后再拆子服务”。
   - AI 服务可直接消费任务队列或事件流；不得为了形式上的分层让所有异步 AI 任务必须绕回业务服务，除非权限、事务或业务主数据一致性明确要求。

10. **模块间数据流转**：

   必须输出 Mermaid 数据流图，不得只输出一行文本箭头：

   ```mermaid
   flowchart LR
     user[用户/浏览器] -->|HTTPS/SSE| gateway[网关]
     gateway -->|REST/gRPC| app[业务服务]
     app -->|任务事件| ai[AI 服务]
     ai -->|向量检索| vector[(Milvus 向量库)]
     ai -->|模型调用| llm[大模型 API]
   ```

   - 图中必须标注同步、异步、流式和存储链路。
   - 如果服务超过 8 个，必须拆成“业务链路图”和“AI 链路图”两张。

11. **反过度拆分检查**：

   | 候选拆分项 | 不拆的理由 | 拆的触发条件 | 当前结论 |
   |------------|------------|--------------|----------|

   - 小项目优先模块化单体或少量服务，禁止为了“看起来像微服务”而拆分。
   - 每个独立服务必须至少满足：独立数据所有权、独立扩缩容、独立发布节奏、明确职责边界中的两个条件。

12. **OpenSpec capability 到服务边界映射**：

   | OpenSpec capability | Requirement / Scenario | 领域模块 | 应用服务 | 部署单元 | 网关能力 |
   |---------------------|------------------------|----------|----------|----------|----------|

   - 每个 OpenSpec capability 必须映射到明确的领域模块、应用服务或网关能力；网关能力名称以 S6 实际选型为准。
   - 无法映射的 capability 必须标记为阻塞项，暂停并输出冲突报告。
   - S7 获批后 OpenSpec baseline 冻结，S8-S30 不得偏离该映射。

13. **DDD 代码骨架目录蓝图**：

   必须输出每个后端服务或模块的 DDD 目录结构，作为 S12/S14 生成代码的唯一目录依据。
   Java/Python/Go 等代码包名或目录名必须短、稳定、代码友好，例如 `report`、`citation`、`knowledge`、`audit`；OpenSpec capability ID 可保留在映射表中，不得强制把很长的 capability ID 原样作为包名或目录名。

   Java / Spring Boot 推荐结构：
   ```text
   src/main/java/<basePackage>/<boundedContext>/
     interfaces/rest/          # Controller、Request、Response、DTO
     application/              # ApplicationService、Command、Query、UseCase
     domain/model/             # Aggregate、Entity、ValueObject、DomainEvent
     domain/service/           # DomainService，仅放领域规则
     domain/repository/        # Repository 接口
     infrastructure/persistence/ # Repository 实现、Mapper、PO
     infrastructure/client/    # 外部服务客户端
     infrastructure/event/     # 事件发布/订阅
     config/                   # 配置
   ```

   Python / FastAPI 推荐结构：
   ```text
   app/<bounded_context>/
     interfaces/api/           # router、schema
     application/              # use_cases、commands、queries
     domain/models/            # aggregate、entity、value_object、event
     domain/services/          # domain_service
     domain/repositories/      # repository interface
     infrastructure/persistence/
     infrastructure/clients/
     infrastructure/events/
   ```

   输出表：

   | 领域上下文 | 服务/模块 | 语言 | 根目录 | DDD 分层目录 | 代码生成责任 Skill |
   |------------|-----------|------|--------|--------------|-------------------|

14. **环境部署边界（承接 S5/S6，供 S24/S27 使用）**：

   | 环境 | 部署形态 | 依赖来源 | 网关入口 | 配置 Profile | 资源约束 |
   |------|----------|----------|----------|--------------|----------|
   | 本地开发 | Docker Compose 最小集 | 优先复用本地 Docker 依赖；不能复用时最小资源容器补齐 | 按 S6 网关选型，本地端口可偏移 | dev | 单容器不超过 2g，禁止默认 GPU / Swarm / K8s |
   | 生产环境 | 按 S6/S7 选型，可为 K8s / 云服务 / 托管中间件 | 生产受控资源 | 统一网关入口 | prod | 按容量规划与生产 SLO |

   - 必须明确哪些服务在本地以容器运行、哪些依赖可复用已有 Docker 容器、哪些生产能力在本地降级替代。
   - 本地开发不得连接生产数据库、生产 MQ、生产对象存储或生产模型密钥。
   - Python AI 服务在本地也应保持内部服务边界；公开入口仍经业务核心或受控网关路由。

## 行为规则

- ✅ 禁止循环依赖
- ✅ 必须先做领域边界识别，再做模块 / 服务 / 部署单元三层拆分
- ✅ 必须输出服务边界决策矩阵和反过度拆分检查
- ✅ 必须输出 OpenSpec capability 到服务边界映射
- ✅ 必须输出 DDD 代码骨架目录蓝图，供 S12/S14 严格使用
- ✅ 模块间数据流转必须使用 Mermaid 图表达，并标注协议/链路类型
- ✅ 混合选型必须明确服务间协议（HTTP/gRPC/WebSocket）
- ✅ 必须区分同步调用、异步任务、事件驱动、流式响应、对象存储回调
- ✅ 必须区分独立部署单元和部署单元内部模块，不能把内部模块误标成独立服务
- ✅ 文件导出/下载必须包含导出状态、对象存储、下载入口、权限校验和访问审计闭环
- ✅ 跨服务审计写入必须明确审计归属，优先通过事件进入审计模块统一落库
- ✅ DDD 包名/目录名必须短、稳定、代码友好；OpenSpec capability 名称只作为需求映射，不强制等同代码包名
- ✅ 必须读取 S6 技术栈表生成后端、网关、消息、存储和 AI 服务边界，不得在技能中默认绑定某个具体项目技术栈
- ✅ 必须输出环境部署边界，区分本地 Docker Compose 最小集与生产部署形态，供 S24/S27 生成容器和部署指南使用
- ✅ 当 S6 选择 Higress 时，Higress 网关模块必须体现路由、鉴权、限流、模型 API 治理职责，并覆盖 Kubernetes Ingress / Gateway API、Nacos/Eureka/Consul 服务发现、Dubbo/Sentinel 治理、大模型 API 代理、多模型 Fallback、Token 级限流/计费、Prompt 安全过滤、语义缓存和 MCP Server 代理
- ✅ AI 项目必须包含 RAG 数据流转设计
- ✅ 输出必须是中文 Markdown 表格
- ❌ 模块粒度不能过细（默认不超过 15 个领域模块，独立部署服务默认不超过 8 个）
- ❌ 不得把模块、应用服务、部署单元混为一谈
- ❌ 不得遗漏任何 OpenSpec capability
- ❌ 模块不能跨层调用（如前端直接调数据层）
- ❌ 不得输出传统 `controllers/services/repositories` 平铺目录作为后端主结构
